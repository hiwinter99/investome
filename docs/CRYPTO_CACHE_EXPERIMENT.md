# 코인 캐시 실험 — Redis 적용 전 기준선

## 먼저 구분할 경로

- `src/api/rankingApi.js`의 코인 요청은 `VITE_RANKING_API_BASE_URL`을 사용하며, 비어 있으면 같은 출처의 `/api/crypto-top30`으로 요청합니다.
- `vite.config.js`의 기본 개발 프록시는 해당 요청을 Vercel API 개발 서버(3000 포트)로 보냅니다.
- `api/crypto-top30.js`: 서버 메모리 300초 캐시, 동시 갱신 요청 병합, 외부 조회 실패 시 이전 목록 반환. CDN 캐시 헤더도 별도로 있습니다.
- 별도 Spring 저장소의 `CryptoMarketService`: 60초 메모리 캐시. 이 실험의 측정 대상은 아닙니다.
- 브라우저에도 60초 캐시가 있습니다. 따라서 페이지 새로고침만으로 백엔드 캐시 성능을 비교하면 여러 캐시 계층이 섞입니다.

## 실행

프로젝트 루트에서 Node.js 24로 실행합니다. 별도 패키지 설치는 필요 없습니다.

```sh
node scripts/benchmark-crypto-cache.mjs work/crypto-cache-baseline.json
```

`work/`는 저장소에서 제외되어 있습니다. 폴더가 없으면 먼저 생성하거나 출력 경로 인수를 생략하세요.

요청량을 늘리려면 다음처럼 실행합니다.

```sh
node scripts/benchmark-crypto-cache.mjs --large
```

큰 실험은 코인 30개를 유지하고 캐시가 있는 상태에서 동시 요청 수 1, 10, 50, 100으로 각각 10,000번씩 요청합니다(총 40,000번 + 첫 요청·만료·오류 확인 102번). 각 단계의 시작과 완료를 표시합니다. 각 작업자는 응답을 받은 뒤 다음 요청을 보내므로, 동시 요청 수는 실제 사용자 수나 초당 고정 유입량을 뜻하지 않습니다. 요청 생성기와 서버가 같은 Node.js 프로세스/PC를 사용하므로 이 결과로 운영 서버의 최대 처리량을 추정할 수 없습니다. warm 단계가 5분 이상 걸리면 실제 TTL 만료가 섞여 검증이 실패할 수 있습니다.

실제 Vercel API 핸들러를 임시 로컬 HTTP 서버에서 실행합니다. 외부 CoinGecko 요청만 150ms 후 30개 가짜 코인을 반환하도록 대체합니다. 인터넷과 운영 서버를 호출하지 않습니다. CDN과 브라우저 캐시도 거치지 않습니다. 테스트가 끝나면 임시 서버는 종료됩니다.

## 읽는 법

- `cold`: 캐시가 없는 첫 요청. 외부 조회 1회가 예상됩니다.
- `warm`: 캐시가 있는 상태. 순차/동시 요청 모두 외부 조회 0회가 예상됩니다.
- `expired`: 시계를 301초 앞으로 옮겨 만료를 재현합니다. 실제 5분 대기 실험은 아닙니다. 기존 요청 병합으로 동시 요청에도 외부 조회 1회가 예상됩니다.
- `upstream failure`: 만료 후 외부 조회 실패 시 기존 목록과 `stale: true`를 반환하는지 확인합니다.
- `averageMs`: 응답 본문 수신과 검증까지의 평균 시간입니다.
- `p95Ms`: 요청 95%가 이 시간 이내에 완료됐다는 뜻입니다. 첫 요청 1개의 p95는 통계적 의미가 없습니다.
- `failures`: HTTP 오류, 타임아웃, 잘못된 응답을 합친 수입니다. 이전 목록 반환은 별도 검증하므로 정상 응답으로 셉니다.
- `requestsPerSecond`: 이 짧은 배치의 관측 처리량입니다. 서버 최대 처리 능력을 뜻하지 않습니다.

수치는 PC 상태, 연결 초기화와 테스트 순서에 영향을 받습니다. 콜드/웜의 짧은 실험 하나로 운영 성능이나 Redis 효과를 주장하지 않습니다.

## 다음 비교

Redis 비교 모드를 추가했습니다. Redis 서버를 실행한 상태에서 먼저 작은 실험으로 연결을 확인합니다.

```sh
node scripts/benchmark-crypto-cache.mjs --redis
node scripts/benchmark-crypto-cache.mjs --redis --large
```

기본 연결은 `redis://127.0.0.1:6379`입니다. 실험마다 고유한 `investome:experiment:crypto:...` 키를 사용하고 종료 시 그 키만 삭제합니다. Redis에 가짜 코인 30개가 실제 저장되고 TTL이 300초 이내인지도 검증합니다. Redis의 시계는 자바스크립트 시계와 별개이므로 만료 실험은 해당 실험 키를 삭제해 캐시 미스를 재현합니다. 실제 Redis의 자연 만료를 기다리는 테스트는 아닙니다.

일반 API는 `REDIS_URL` 환경 변수가 있으면 Redis를, 없으면 기존 메모리 캐시를 사용합니다. 로컬 Vercel 개발 서버에 연결하려면 무시되는 `.env.local` 파일에 `REDIS_URL=redis://127.0.0.1:6379`를 설정하고 개발 서버를 재시작합니다. 실제 API 키는 `investome:crypto:top30:v1`이며 실험 키와 다릅니다. 배포 환경에서는 접근 가능한 별도 Redis 주소가 필요합니다. 이번 작업에서는 운영 설정을 바꾸지 않습니다.

정상 Redis 조회는 매 요청 Redis를 사용합니다. 성공한 목록은 프로세스 메모리에도 보관해 Redis 장애 시에는 기존 5분 메모리 캐시를 사용하고, 외부 API까지 실패하면 이전 목록을 `stale: true`로 반환합니다. 이전 목록은 현재 프로세스에만 남으므로 재시작 후까지 보장하지 않습니다. 동시 갱신 병합도 프로세스 안에서만 수행합니다. 여러 서버가 동시에 캐시 미스를 만났을 때의 분산 잠금은 아직 구현하지 않았습니다.

자동 검증(네트워크 없이 가짜 Redis 사용):

```sh
node --experimental-test-module-mocks --test scripts/crypto-redis.test.mjs
```

실제 Redis 연결과 성능은 위 `--redis` 실험에서 별도로 확인합니다. 서버 두 개의 캐시 공유 비교는 다음 단계입니다.

이 실험은 합성 데이터 기반 로컬 검증이라고 명시하고, 실제 운영 사용자나 운영 성능 개선 수치로 표현하지 않습니다.

## 두 서버의 캐시 공유 실험

```sh
node scripts/benchmark-crypto-shared-cache.mjs
```

Redis를 켜두고 실행합니다. 각 모드마다 별도의 Node.js 프로세스 A/B를 띄우고, A 첫 요청 → B 첫 요청 → A 재요청 → B 재요청 순서로 직접 HTTP 요청합니다. PID가 다른지 확인하고 응답 데이터와 외부 조회 횟수를 검증합니다. 가짜 외부 API는 각 프로세스에서 150ms 후 응답하며 인터넷에는 연결하지 않습니다.

메모리는 A/B가 각각 외부 조회 1회씩(총 2회), Redis는 A만 1회 조회하고 B는 공유된 데이터를 사용(총 1회)하는 것이 예상 결과입니다. 누적 외부 호출 수를 표시하므로 재요청 행의 숫자를 더하지 마세요. Redis 키는 실행별 UUID로 격리하고 종료 시 해당 키만 삭제하며 서버 프로세스도 종료합니다.

이것은 캐시 공유 기능 검증이며 부하/고가용성/로드 밸런싱 실험은 아닙니다. A가 저장을 끝낸 뒤 B에 요청하므로, 동시에 두 서버에 최초 요청이 들어오는 경우의 중복 조회를 방지했다고 주장할 수 없습니다. 로컬 HTTP 응답 시간은 참고값입니다.
